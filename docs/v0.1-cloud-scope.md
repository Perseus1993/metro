## 定位

v0.1 是**批量实验跑批服务**，不是算法平台。

价值主张：本地跑不动的参数扫描（几十个 seed × 场景组合），云上一晚出结果。
算法代码定制推迟到 v0.2 —— 届时复用已有的 `RoutingPluginProcessHost` 与 10 用例契约套件。

**这一点必须提前和学弟对齐**，否则他会以为 v0.1 能跑他自己的算法。

## 必须交付

### 1. JobSpec v0.1（唯一不能返工的东西）

**白名单**，不是 CLI 参数透传。任何 `Path` 类型参数（`--goal-graph-config`、`--routing-plugin-manifest`）一律不暴露，否则是路径注入。

```json
{
  "spec_version": "0.1",
  "station": "小寨",
  "hour": 18,
  "design_template": "visual_demo_station",
  "minutes": 30,
  "demand_minutes": 30,
  "clearance_minutes": 0,
  "tick_seconds": 1,
  "group_size": 1,
  "seed": 42,
  "entry_count_hour": null,
  "exit_count_hour": null,
  "transfer_count_hour": 0,
  "movement_backend": "jupedsim",
  "jupedsim_model": "collision_free_speed",
  "routing_algorithm": "builtin_shortest_path",
  "trajectory_sample_seconds": 1
}
```

- 枚举值全部服务端校验，非法值 400 而不是让 worker 崩。
- `station` / `design_template` 校验存在性。
- `minutes × group_size` 设上限，防止一个 job 打满机器。
- 版本号写死 `0.1`，v0.2 加字段时新开 `0.2` 并保持 `0.1` 可用。

### 2. Parquet 轨迹导出器（最大工时块）

现有 `simulation_outputs/visual_tracks.py` 产出的是给渲染器的嵌套结构，不适合分析。新写一个从 `frames` 直出的扁平导出器，**不要**在 visual_tracks 之上转换。

`trajectories.parquet`（长表）:

| 列 | 类型 | 说明 |
|---|---|---|
| agent_id | int32 | |
| t_seconds | float32 | 仿真时间 |
| x, y | float32 | 米，坐标系 id 记在 manifest |
| level_id | category | |
| phase | category | |
| state | category | |

`events.parquet`: terminal events + facility service events 合并成长表（agent_id, t_seconds, event_type, facility_id, detail）。

`summary.json`: 回显 JobSpec、schema_version、agent 总数、清空时间、墙钟耗时、坐标变换 id。

**注意体积**：1 秒 tick、逐 agent，30 分钟高峰场景很容易到几百 MB。`trajectory_sample_seconds` 参数必须在 v0.1 就有，默认可考虑设 1 但让学弟能调大。按 `agent_id` 分区或排序后 zstd 压缩。

### 3. API 层（新写，不动 designer server）

FastAPI，4 个端点，静态 Bearer token：

```
POST /v1/jobs              -> {job_id}          提交 JobSpec
GET  /v1/jobs/{id}         -> {status, progress, error}
GET  /v1/jobs/{id}/files   -> 产物清单 + 大小
GET  /v1/jobs/{id}/files/{name}  -> 下载（支持 Range）
```

`apps/station_designer/server.py` **保持不动**，继续做本地工具。

### 4. Job 存储与 worker

- SQLite 一张 `jobs` 表：id, spec_json, status, progress, error, created_at, updated_at, output_dir。
  替换现有 `comparison_jobs.py` 里 `_JOBS: dict` + `MAX_COMPARISON_JOBS = 20` 的进程内存方案（重启即丢）。
- worker 是独立进程，轮询 SQLite 取 queued job，`subprocess` 调现有 `metro-station simulate`，产物落 `/data/jobs/{id}/`。
- 单 worker 串行即可。加 systemd 自动重启。
- 磁盘保留策略：保留最近 N 个 job 或 N GB，超了删最旧的。**别忘了这条**，否则两周后磁盘满。

### 5. 客户端 SDK（学弟唯一接触的面，最该打磨）

```python
from metro_cloud import Client

c = Client(url=..., token=...)
job = c.submit(station="小寨", hour=18, seed=42, minutes=30)
job.wait()                      # 带进度条
df = job.trajectories()         # -> pandas DataFrame
ev = job.events()
meta = job.summary()

# 批量扫描
jobs = c.submit_many([dict(seed=s, hour=h) for s in range(20) for h in (8, 18)])
```

本地缓存已下载的 parquet，避免重复下载。
