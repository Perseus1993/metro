# PM-032：PyTorch 运动与可微标定 P0 可行性计划

- 状态：`proposed`
- 计划日期：2026-08-02
- 计划类型：Phase 0 技术与科研可行性门
- 产品优先级：P2 战略探索，不是 V0.2 发布阻断级 P0
- 预计投入：8～12 人日，建议 2 个自然周内完成
- 决策对象：是否投入 P1 建设正式 `TorchMovementBackend`、批量实验和可微标定能力
- 当前产品影响：不改变 V0.2 功能冻结、真实用户门禁或 `hold` 决定

## 1. 管理结论

批准一个限时、可撤销、证据优先的 P0，但不批准“重写 PyTorch 版 Metro”。

P0 只验证以下命题：现有 Metro 能否在不改变 Goal、设施、列车、排队、运行顺序和证据合同的前提下，接入一个内部 PyTorch 运动后端；该后端能否在目标负载上形成有意义的 GPU 批处理收益；连续运动参数能否通过自动微分完成可核验的合成标定。

P0 的交付物不是新产品版本，也不是可用于真实运营的行人模型。最终必须形成 `go-acceleration`、`go-calibration`、`limited-go` 或 `stop` 四选一决策，禁止用“Demo 能运行”代替投资判断。

## 2. 术语和战略位置

本文的 **P0** 指 Phase 0 可行性验证。现有产品 Backlog 中的 **P0** 指 V0.2 黄金路径阻断项，两者不得混淆。

当前 V0.2 只产品化 `evacuation-routing/v1`。ADR-007 已把策略选择、全局路由、局部运动和实验优化定义为四个独立边界，并明确运动接口尚未形成第三方 SDK。因此 PM-032：

- 不进入 V0.2 当前发布范围；
- 不改变 V0.2 的 `hold` 原因；
- 不开放第三方运动插件；
- 不替代 JuPedSim 基线；
- 只为后续科研路线减少一项关键不确定性。

## 3. 战略意图

### 3.1 要解决的用户问题

**首要用户：** 需要研究行人运动参数、批量敏感性或学习型行为模块的仿真算法研究者。

**当前问题：** Metro 已能进行可复现案例、配对种子和算法比较，但现有 JuPedSim/C++ 运动内核不向 PyTorch 自动微分暴露计算图。研究者无法直接回答以下问题：

1. 哪些连续运动参数最能解释观测轨迹或宏观流量差异；
2. 梯度标定是否比黑箱参数搜索更节省仿真预算；
3. 多案例、多种子并行时，GPU 是否能缩短实验周转时间；
4. 学习型局部行为能否在不接管 Goal 和设施流程的情况下接入。

### 3.2 P0 支持的决策

P0 只支持一个投资决策：

> Metro 是否应把“可选 PyTorch 局部运动与可微标定后端”列入 P1 研发，而不是继续只把 PyTorch 当作概念性方向。

### 3.3 为什么不是整体重写

Metro 的 Goal Graph、设施服务、队列、列车时刻、容量、管控时间轴和证据输出是离散状态机与领域规则，不因改成 Tensor 就自然获得性能或可信度。整体重写会同时改变行为权威、运行顺序和证据来源，破坏现有配对实验的归因能力。

合理边界是：

```text
Goal Graph / 设施 / 排队 / 列车 / 管控 / 证据
                        |
                 MovementBackend
                  /           \
          JuPedSim 基线    Torch P0 后端
```

### 3.4 社区证据如何影响本计划

- [VMAS](https://github.com/proroklab/VectorizedMultiAgentSimulator) 证明了 PyTorch 二维多智能体仿真、批量环境和自动微分在工程上可行；其固定 agent 数量限制说明 Metro 应采用固定槽位和 active mask，而不是动态改变 Tensor 形状。
- [AgentTorch](https://openreview.net/forum?id=JlBBoZBOeF) 支持“Tensor 化 ABM + 自动微分标定”的研究方向，但案例集中在疫情、意见和生物网络，不能作为站内行人动力学有效性的证据。
- [Deep Social Force](https://github.com/svenkreiss/socialforce) 可作为可微行人相互作用的算法参考，但不能替代 Metro 自己的验证。
- [TorchDriveSim](https://github.com/inverted-ai/torchdrivesim) 的固定容量和 present mask 设计值得借鉴；它允许 agent 重叠且不提供站内行人行为，因此不是可直接替换的运动引擎。
- AgentTorch 当前仓库的 `LICENSE.md`/README 为 AGPL-3.0，而包元数据曾出现 MIT 标注；VMAS 为 GPLv3。P0 只借鉴公开论文与架构思想，禁止复制这两个仓库的实现代码。

### 3.5 产品优先级评分

按当前产品 operating model 作初始评分：

| 维度 | 分值 | 假设 |
|---|---:|---|
| 用户影响 | 3/5 | 对算法研究者价值明确，但不是当前全部教师/学生黄金路径的共同阻塞 |
| 战略匹配 | 2/5 | 支持未来实验方法与校准，不能推进 V0.2 真实用户 UAT |
| 证据增益 | 5/5 | 能减少“PyTorch 是否值得研发”的核心技术与科研不确定性 |
| 紧迫度 | 3/5 | 需要尽早回应研究方向，但等待两个自然周不会破坏现有产品 |
| 工作量 | 3/5 | 8～12 人日，跨环境、数值、适配和证据 |
| 风险 | 4/5 | 模型可信度、几何、动态人数、梯度和性能交叉点均未验证 |

优先级分数：

`(2×3 + 2×2 + 5 + 3) / (3 + 4) = 18/7 = 2.57`

该分数支持“批准限时探索”，不支持挤占 V0.2 真实用户门禁或直接承诺 P1。

## 4. 待验证假设

| ID | 假设 | 验证方法 | P0 通过条件 |
|---|---|---|---|
| H1 | 现有运动端口足以隔离 Torch | 接入内部后端并运行生命周期、动态几何和完整站型 smoke | 不修改 Goal/设施权威，不向 Torch 暴露 Mesa Agent，不改变 tick 阶段顺序 |
| H2 | Tensor 内核能满足基础运动约束 | 自由行走、对向、走廊、瓶颈、墙体、生成/移除微场景 | 无 NaN/Inf、越界、身份泄漏或持续严重穿透；轨迹证据完整 |
| H3 | GPU 在目标批量负载上有收益 | 同一 Torch 内核 CPU/CUDA 基准，分离内核与端到端耗时 | 至少一个目标批量负载达到预设加速门；不把不同物理模型的耗时差写成公平速度结论 |
| H4 | 连续参数梯度可用于标定 | 有限差分梯度核验和合成参数恢复 | 梯度误差、损失下降和参数恢复达到阈值 |
| H5 | 新后端能进入现有证据链 | 输出 `movement_trace.v1`、运行元数据和失败诊断 | 报告能区分后端、设备、dtype、参数、版本和确定性设置，且无静默降级 |

## 5. P0 范围

### 5.1 必须交付

1. 独立、锁版本的 Torch 开发环境和安装说明；`torch` 保持可选依赖。
2. 一个内部 `TorchMovementBackend` 原型，实现批量 `step_all`、合法放置、移除、活动 ID、动态几何刷新和运动轨迹。
3. 固定容量 Tensor 状态、active mask 和 passenger-ID/slot 双向映射。
4. 一个最小碰撞感知运动内核：目标速度、速度/加速度限制、乘客排斥、墙体排斥、积分和到达判断。
5. CPU eager 与 CUDA eager 两种执行路径，首轮统一使用 `float32`；梯度核验允许 `float64`。
6. 七类确定性微场景、一个 50 人正式站型薄切片和一个动态管控几何场景。
7. 内核性能矩阵、端到端运行证据、显存/内存证据和确定性证据。
8. 至少两个连续参数的合成标定实验。
9. 一份含失败样本、限制、原始结果和四选一结论的 P0 决策报告。

### 5.2 明确非目标

- 不宣称与 JuPedSim 轨迹等价或科学上更真实；
- 不移除、降级或绕过 JuPedSim；
- 不把 Torch 后端设为默认值；
- 不把运动接口开放为第三方 SDK；
- 不实现 RL、LLM agent、AgentTorch runner 或 VMAS 场景系统；
- 不实现百万行人、分布式训练或多 GPU；
- 不在 P0 优化空间哈希、自定义 CUDA、NVIDIA Warp 或 `torch.compile`；
- 不让离散排队、上车、列车容量和设施开关进入 autograd；
- 不进行现场数据校准，不生成真实运营、安全认证或数字孪生措辞；
- 不为 Torch 另建一套实验执行器、报告格式或可视化事实来源。

## 6. 目标技术边界

### 6.1 状态布局

每个批量环境采用固定容量 `Nmax`：

| Tensor/映射 | 建议形状 | 含义 |
|---|---|---|
| `position` | `[B, Nmax, 2]` | 当前二维位置 |
| `velocity` | `[B, Nmax, 2]` | 当前速度 |
| `target` | `[B, Nmax, 2]` | 当前局部目标 |
| `radius` | `[B, Nmax, 1]` | 身体半径 |
| `desired_speed` | `[B, Nmax, 1]` | 自由流速度 |
| `active_mask` | `[B, Nmax]` | 当前是否参与计算 |
| `level_index` | `[B, Nmax]` | 所属楼层；不同楼层不得相互作用 |
| `id_to_slot` | Python 映射 | passenger ID 到固定槽位 |
| `slot_to_id` | 长度 `Nmax` | 固定槽位到 passenger ID |

固定槽位避免上下车和到离站导致 Tensor shape 变化。删除乘客只清除 active mask，复用槽位前必须清空其速度、目标、轨迹 episode 和梯度相关状态。

### 6.2 P0 运动方程

P0 使用自主实现的最小连续内核，不复制第三方代码：

1. 根据当前位置和局部目标计算期望方向；
2. 根据自由流速度得到期望速度；
3. 使用光滑距离函数计算乘客间排斥；
4. 使用预处理墙段计算边界排斥；
5. 合成加速度并执行加速度、速度上限；
6. 按物理时间步积分位置；
7. 在适配器边界执行合法域核验和必要的安全投影；
8. 到达判断沿用后端无关的目标半径语义。

乘客邻域在 P0 允许 `O(N²)`，但必须单独记录其增长曲线。只有 P1 才评估 cell list、空间哈希或 Warp kernel。

### 6.3 几何边界

- Shapely 继续作为权威几何构建和合法性检查，不进入 Torch step 内环。
- 每层可步行边界在初始化或管控事件后预处理为墙段 Tensor；P0 不要求可微几何生成。
- `on_walkable_geometry_changed` 必须在一个 tick 内刷新对应层的墙段和合法域版本。
- 动态障碍作用时，现有乘客不得因刷新被静默删除；无法恢复合法位置必须显式失败。

### 6.4 自动微分边界

允许学习的 P0 参数限定为连续量，例如排斥强度、作用距离、松弛时间或自由速度修正。损失使用检查点位置/速度 MSE 或连续密度代理。Goal 切换、队列进入、设施容量、列车到发和终止事件不承诺可微。

### 6.5 依赖和运行环境

- 新增独立可选 extra，例如 `metro-station[torch]`，基础安装不得下载或导入 Torch。
- 本机 RTX 3080 20 GB 可作为 P0 CUDA 目标硬件。
- 当前 Anaconda 基础环境导入 Torch 出现重复 OpenMP 运行时错误。P0 必须使用新的 uv/venv 锁定环境；禁止设置 `KMP_DUPLICATE_LIB_OK` 掩盖问题。
- P0 记录 Python、Torch、CUDA、驱动、GPU、dtype、device、确定性设置和代码版本。

### 6.6 计划中的代码落点

以下是建议落点，不是已实现状态：

```text
packages/metro_station/src/metro_station/adapters/simulation/movement/
  torch_backend.py       # 当前 MovementBackend 到 Tensor kernel 的适配
  torch_kernel.py        # 不接收 Mesa Agent 的纯 Tensor 内核
  torch_state.py         # 固定槽位、active mask、ID/slot 生命周期
  torch_geometry.py      # Shapely 权威几何到只读墙段 Tensor

experiments/metro_station_experiments/src/metro_station_experiments/
  torch_movement_p0.py   # 微场景、benchmark、标定和证据汇总入口

tests/
  test_torch_movement_contract.py
  test_torch_movement_micro_scenarios.py
  test_torch_movement_gradients.py
```

当前内部 `MovementBackend` 仍接收 `PassengerAgent`；只有 `torch_backend.py` 适配层可以接触该对象。`torch_kernel.py` 必须只接收值对象或 Tensor，避免把当前 Mesa 类型冻结成未来公共运动协议。

### 6.7 计划中的单一执行入口

P0 应提供一个不依赖仓库私有知识的入口，名称可在实现评审时调整：

```powershell
uv run --extra torch metro-station-experiment torch-movement-p0 `
  --device-matrix cpu,cuda `
  --output docs/product/evidence/PM-032
```

该入口负责运行预检、微场景、正式站型 smoke、性能矩阵、梯度检查和合成标定；任一子项失败时仍写出完整索引和失败证据，并返回非零退出码。

## 8. 验证场景与实验矩阵

### 8.1 微场景

| 场景 | 人数 | 主要验证 |
|---|---:|---|
| M1 单人自由行走 | 1 | 单位、时间步、速度上限、目标到达 |
| M2 对向相遇 | 2 | 对称破局、避碰、无长期锁死 |
| M3 双向走廊 | 32/100 | 车道形成倾向、吞吐、`O(N²)` 增长 |
| M4 单瓶颈 | 50/100/300 | 拥堵、墙体、持续穿透和数值稳定性 |
| M5 生成与移除 | 峰值 100 | 固定槽位复用、active ID 和轨迹 episode |
| M6 多楼层隔离 | 每层 20 | 不同楼层无错误相互作用；跨设施前后重放置 |
| M7 动态障碍 | 50 | 几何刷新、事件 tick 对齐和合法位置恢复 |

### 8.2 正式站型薄切片

- 使用固定版本的 `visual_demo_station` 或等价正式预设；
- 50 人、固定种子、单一后端变量；
- 完成生成、行走、设施服务、终止、轨迹导出和人数守恒；
- JuPedSim 与 Torch 使用同一案例输入，但报告明确二者物理模型不同；
- 不把清场时间差直接解释为性能或真实性差异。

### 8.3 性能矩阵

| 维度 | 取值 |
|---|---|
| Torch device | CPU、CUDA |
| 环境批量 `B` | 1、8、32 |
| 活动人数 `N` | 32、100、300、1024（1024 仅内核压力） |
| dtype | float32；float64 仅用于梯度核验 |
| 执行方式 | eager；`torch.compile` 不进入 P0 结论 |
| 重复 | 至少 20 次 warm-up、100 次测量、5 轮独立重复 |
| 指标 | step p50/p95、agent-step/s、端到端 wall time、CPU 内存、CUDA 峰值显存、主机/设备传输次数 |

CUDA 计时必须在测量边界同步或使用 CUDA events。内核吞吐和完整 Metro wall time分开报告，禁止只展示最有利数字。

## 9. P0 验收门禁

### 9.1 产品价值门

- 一名仿真研究者可通过一个文档化命令选择 JuPedSim 或 Torch，不能修改核心代码后才能切换。
- 一条命令可运行微场景、性能和合成标定并生成证据索引。
- 报告能直接回答：可接入吗、约束通过吗、GPU 交叉点在哪里、梯度可用吗、下一步做什么。
- 报告明确“未校准、非生产、非安全认证、非 JuPedSim 等价实现”。

### 9.2 仿真可信度门

以下阈值是 P0 工程阈值，不是现场有效性标准：

1. 所有场景无 NaN/Inf，人员守恒误差为 0，活动 ID 集合与 Metro 权威乘客集合一致。
2. M1 在无相互作用时的中位速度误差不超过目标速度的 2%，到达时间误差不超过解析值的 5%。
3. 所有墙体场景不得出现超过 1 cm 的域外位置。
4. 任意乘客对超过 5 cm 的持续穿透若连续超过 0.2 s，场景判定失败；全部穿透事件仍需进入报告。
5. M2 不得在目标未完成时连续 5 s 净位移小于 0.3 m。
6. M5 每次移除后后端 active ID 立即消失；槽位复用不得继承前一乘客速度、目标或 episode。
7. M7 的几何更新在目标时刻一个 tick 内生效，计划/应用时刻与现有管控证据一致。
8. 固定 seed、环境、device 和 dtype 的 CPU 重复最大位置差不超过 `1e-5 m`；CUDA 不超过 `1e-4 m`。跨设备只比较容差和统计量，不要求逐位一致。

### 9.3 工程就绪门

- 默认 `metro-station` 安装和 import 不依赖 Torch；缺少 extra 时选择 Torch 后端会得到可诊断错误，不能回退 JuPedSim。
- 不改变 ADR-004 规定的 tick 阶段顺序、随机数顺序和人数守恒合同。
- 不让 domain/application 导入 Torch；Torch 实现只位于 adapter/experiment 边界。
- `movement_trace.v1` 保持兼容；新增的 backend/device/dtype/parameter metadata 为可选字段，并通过旧 reader 测试。
- 现有 JuPedSim 定向测试、架构契约和正式站型 smoke 保持基线状态；若基线已有失败，必须冻结并单独列示。
- 代码和证据中不存在 `KMP_DUPLICATE_LIB_OK`、静默 CPU 回退或未记录的设备切换。

### 9.4 性能门

- P0 不要求单场景 `B=1` 的 Torch GPU 快于 JuPedSim。
- 对同一 Torch 物理内核，`B=32, N=300` 时 CUDA 的 `agent-step/s` 至少为 CPU 的 2 倍，或在另一个预先声明的目标批量点达到 2 倍；不得事后挑选未声明点。
- `B=32, N=300` 峰值显存不超过 16 GB，为 20 GB 目标卡保留运行余量。
- 测量轮次 p95/p50 不高于 1.5；若不稳定，必须诊断同步、分配或数据传输。
- 每个 Torch step 内不得把完整位置状态往返拷贝 CPU/GPU；主机只接收 Metro 所需的最终 step 结果和证据采样。

性能门只决定是否进入“批量加速 P1”，不单独否决“可微标定 P1”。

### 9.5 自动微分门

- 在 M1/M3 的光滑损失上，对至少两个参数执行 autograd 与中心有限差分比较；相对误差不超过 5%。
- 从偏离真值至少 20% 的初值出发，用合成轨迹恢复至少两个参数；最终相对误差不超过 10%，损失较初值下降至少 80%。
- 标定过程不得通过修改目标轨迹、seed 或离散事件时序降低 loss。
- 若安全投影造成梯度截断，必须分别报告投影前可微内核和投影后实际运动，不能宣称端到端全部可微。

## 10. 三轴退出判定

| 轴 | `pass` 条件 | `conditional` 示例 | `fail` 条件 |
|---|---|---|---|
| 产品价值 | 研究者能复跑并据证据选择下一步 | 只能由开发者运行，但报告完整 | 只能展示动画或无法回答投资问题 |
| 仿真可信度 | H2、H4 和证据披露通过 | 基础约束通过，但部分拥堵场景失败且已限定边界 | 人数/身份/几何/梯度证据不可信或失败被隐藏 |
| 工程就绪 | 可选依赖、端口隔离、回归和可诊断失败通过 | 性能不足但代码边界可靠 | 改变 Goal/设施权威、破坏旧合同或需要不安全环境绕过 |

## 11. 最终投资决策规则

### `go-acceleration`

H1、H2、H3、H5 全部通过，且批量实验是被确认的目标工作负载。允许进入 P1：批量仿真执行、邻域优化、真实负载性能和更完整几何。

### `go-calibration`

H1、H2、H4、H5 通过，但 H3 未达到加速门。允许进入 P1：可微参数、轨迹/密度损失、合成与真实数据协议；不得宣传 GPU 加速。

### `limited-go`

端口和基础内核成立，但性能、拥堵约束或梯度只在窄场景有效。原型保留在实验边界，用于论文方法探索，不进入正式产品后端。

### `stop`

满足任一条件即停止：

- 为接入 Torch 必须改变 Goal、设施、队列或 tick 权威；
- 动态增删、楼层隔离或几何刷新不能稳定表达；
- 严重穿透、NaN/Inf 或身份泄漏不能在时间盒内解决；
- 梯度检查无法通过，且没有独立的批量加速价值；
- 环境只能依赖不安全 OpenMP 绕过；
- 只有通过复制 GPL/AGPL 实现才能完成；
- 团队把模型差异、动画观感或单个速度数字当作科学有效性证据。

## 12. 风险与控制

| 风险 | 早期信号 | 控制措施 |
|---|---|---|
| 不同运动模型导致错误“性能对比” | 直接比较 JuPedSim 和 Torch wall time并称加速 | 同内核 CPU/GPU 才是性能主比较；跨模型只作系统成本背景 |
| 动态人数导致重编译/分配 | 每次生成或离站创建新 Tensor | 固定槽位、active mask、预分配；P0 不启用 compile |
| `O(N²)` 在高密度失控 | N 翻倍时 step 接近 4 倍 | 明确记录曲线；P1 再引入 cell list/Warp |
| 安全投影切断梯度 | loss 有值但参数 grad 为零/异常 | 分离光滑内核与安全投影，做有限差分和投影触发率报告 |
| 几何预处理与 Shapely 权威漂移 | Tensor 墙段和合法域版本不一致 | 几何版本号、事件后重建、随机采样一致性核验 |
| 依赖污染基础包 | 无 CUDA 用户也安装大型 Torch wheel | 可选 extra，CI 分基础/torch 两档 |
| 复现性被夸大 | CPU/GPU 轨迹差异被隐藏 | 记录设备与容差；跨设备比较统计，不承诺逐位一致 |
| 许可传染 | 直接复制 AgentTorch/VMAS 类或函数 | clean-room 独立实现；保留来源笔记；复用前单独许可评审 |
| P0 挤占 V0.2 UAT | 工程继续扩功能而真实用户门禁无人执行 | 独立时间盒和负责人；P0 不改变 V0.2 `hold` 与冻结范围 |

## 13. 资源和节奏

建议角色而非指定个人：

- 仿真/架构负责人：端口、生命周期、运行顺序和回归；
- 数值/算法负责人：运动方程、梯度检查和标定；
- 证据评审人：场景、阈值、性能方法和结论措辞独立复核。

一人可以承担前两项，但 P0-09 必须由未编写核心内核的人复核原始证据。

建议节奏：

| 时间 | 目标 |
|---|---|
| 第 1～2 天 | 基线、隔离环境、端口契约 |
| 第 3～5 天 | Tensor 状态和最小 CPU/CUDA 内核；第一次继续/停止评审 |
| 第 6～7 天 | Metro 适配、生命周期和动态几何 |
| 第 8 天 | 微场景和正式站型薄切片 |
| 第 9 天 | 性能矩阵和显存证据 |
| 第 10 天 | 梯度检查、合成标定、决策评审；预留 2 人日处理证据缺口 |

## 15. P1 只有在 P0 后才能定义

P0 之前不承诺 P1 范围。若通过，对应方向分别为：

- **加速 P1：** 批量 SimulationExecutor、邻域搜索、几何缓存、多种子实验预算和目标硬件验收；
- **标定 P1：** 版本化可学习参数、轨迹/密度损失、数据切分、参数不确定性和外部验证协议；
- **双通过 P1：** 两条路线共享同一 Torch 内核，但使用独立退出指标，不能用加速证据替代标定证据。

无论哪条路线，正式运动模型 SDK、默认后端切换、真实数据有效性和运营用途都需要新的 ADR、产品需求和发布证据。
