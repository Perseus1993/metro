# PM-028-E3 需求—故障耦合试探包

- 优先级：P1
- 状态：`implemented / 252 of 252 runs passed`
- 依赖：E1拓扑核心矩阵通过；E2关键合同边界稳定；现有时间轴和运营故障内核

## 实际结论（2026-07-18）

- 12个基线配置 + 72个需求—故障配置，使用41/42/43三个种子，共252次全部通过；
- 分段需求、入口权重、生成入口核算和动态列车容量已进入正式场景/运行合同；
- F3扶梯换向使用关闭—排空—换向—开放的安全时间轴；F5拆分为满载容量与服务中断两种可观察行为；
- 每tick人员核算最大误差为0，所有动态事件按计划tick应用，终态清场和重复运行语义指纹满足断言。

## 要回答的问题

静态拓扑正确不代表高偏流、对冲流或列车脉冲下仍能合理运行。E3验证拓扑、需求与动态故障叠加时，事件是否真实生效，旅客是否重新规划，人员与设施事实是否完整进入快照、报告和回放。

## 安全边界

- 本包比较软件行为，不根据单次或少量种子得出真实运营优劣结论。
- 清场、排队和密度只作模型内诊断；没有现场校准时不作真实容量或安全声明。
- 当前若没有旅客无障碍属性合同，只验证“电梯路径是否存在/丢失”的拓扑事实，不宣称无障碍旅客行为已验证。

## 四个拓扑基例

| ID | 形态 | 跨层 | 付费区 | 用途 |
|---|---|---|---|---|
| `TB1` | 两层矩形 | 单完整连接簇 | 双向闸机 | 控制组 |
| `TB2` | 两层L形、多入口 | 双连接簇 | 进出分离 | 入口偏流和替代路径 |
| `TB3` | 三层T形 | 相邻层接力 | 进出分离 | 接力换乘与单段故障 |
| `TB4` | 三层瓶颈形 | 双完整连接簇 | 双向闸机 | 远距离重路由和窄颈排队 |

每个基例含至少两部电梯、楼梯和一对扶梯，使五类故障都有有效目标。E1已确认支持 `CHAIN`，因此 `TB3` 以三层相邻层接力形态进入 `VALID` 运行矩阵。

## 三种需求形态

所有需求使用15分钟窗口，需求结束后继续运行到清场或声明的最大观察时间。实际人数由需求合同计算并写入证据。

| ID | 定义 | 目的 |
|---|---|---|
| `D1-SKEW` | 总进站900人/小时；多入口按90%/10%分配；少量出站作为背景 | 验证入口极度不均与闸机选择 |
| `D2-COUNTER` | 进站600人/小时 + 出站600人/小时，同时发生 | 验证闸机与跨层设施双向对冲 |
| `D3-PULSE` | 0～5分钟200人/小时背景；5～7分钟1200人/小时换乘/列车到达脉冲；7～15分钟恢复背景 | 验证队列积累、消散与列车事件耦合 |

版本化需求输入现已通过 `DemandSegment` 和入口权重表达分段到达率与来源分配；测试只走正式输入和生成入口核算，不直接篡改agent列表。

## 五类动态故障

每个故障在第5分钟应用，第9分钟恢复；列车中断按正式列车事件语义执行。

| ID | 动作 | 核心断言 |
|---|---|---|
| `F1-ELEVATOR` | 关闭一个完整电梯簇 | 关闭后不再接纳新服务；替代跨层路径或明确不可达 |
| `F2-STAIRS` | 关闭主要楼梯 | 路径重算，楼梯状态、队列和事件一致 |
| `F3-ESCALATOR` | 反转一条扶梯方向，再恢复 | 一个tick内生效；方向、运行设施和回放标记一致 |
| `F4-GATE` | 关闭主要入口或出口闸机组的一半lane | 关闭lane不服务；其他lane接管并记录队列压力 |
| `F5-TRAIN` | 列车满载或服务中断，再恢复 | 乘车终态不被提前授权；恢复后可继续完成 |

`F5` 在机器目录中拆成 `F5A-TRAIN-FULL` 与 `F5B-TRAIN-OUTAGE` 两个子case。产品上仍属于一个列车故障家族，但运行规模按两个独立故障变体计算。

## 运行矩阵

- 正常基线：`4拓扑 × 3需求 = 12`；
- 非列车故障：`4拓扑 × 3需求 × 4故障 = 48`；
- 列车故障：`4拓扑 × 3需求 × 2变体 = 24`；
- 故障组合合计：`48 + 24 = 72`；
- 固定种子：`41, 42, 43`；
- 计划运行：`(12 + 72) × 3 = 252` 次；每个故障运行引用同种子的正常基线。

每个故障案例必须引用同拓扑、同需求、同种子的正常基线指纹。除故障时间轴外，不允许站型、需求、模型参数和随机种子漂移。

## 执行阶段

1. 预检设计、拓扑、需求和故障目标；目标不存在时运行前拒绝。
2. 运行正常基线并保存输入指纹、事件计划和指标摘要。
3. 运行故障配对，记录计划时刻、应用时刻、恢复时刻和拒绝原因。
4. 检查每tick人员守恒、设施状态、队列、目标变化和终态授权。
5. 生成差异报告，但不自动给出真实运营“更优/更安全”结论。
6. 对每种拓扑至少选一个案例生成回放并检查事件标记。

## 必须通过的工程断言

- 事件在目标时刻一个tick内应用，计划事实和应用事实均被记录；
- 关闭设施应用后不接纳新的服务，恢复前状态不自发回滚；
- 不可达旅客保留明确状态和阻断原因，不消失、不瞬移、不非法完成；
- `spawned = active + completed + legitimately_removed` 的人员核算每tick成立；
- 所有数量、位置、时间、密度和队列指标为有限数且不为负；
- Goal Graph仍是战略行为权威，展示层不能改变旅客目标；
- 固定种子同环境复跑的语义指纹一致；
- right-censored只用于达到观察窗口但人员仍有合法状态的 `STRESS` 案例。

## 诊断指标

必须记录但不作为未经校准的真实阈值结论：

- 完成率、right-censored和剩余人数；
- 清场时间或未清场原因；
- 最大闸机/跨层队列、队列持续时间；
- 峰值站内人数和模型内局部密度；
- 各设施服务人数、利用率和关闭期间服务增量；
- 重路由次数、不可达次数和阻断原因分布；
- 事件应用偏差、恢复偏差；
- 仿真耗时与错误率。

不设置“故障后清场一定更慢”等脆弱单调断言，因为旅客选择与队列可能改变。只要求事实自洽，并把配对差异作为观察证据。

## `VALID`、`STRESS` 和失败规则

- 正常基线和有替代路径的故障默认为 `VALID`；
- 故意关闭唯一可达路径的案例为 `STRESS`，允许right-censored；
- 故障目标不存在、方向动作不兼容或时间窗口冲突为 `INVALID`，必须运行前拒绝；
- 崩溃、人员核算错误、非法终态、无诊断fallback或非有限数在任何分类下都是失败。

## 证据

`summary.json` 需包含12个基线配置、72个故障配置、252次实际运行、3种子覆盖、五类故障家族、两类列车子case、人员守恒最大误差和失败列表。每个失败保留事件计划、首个违规tick、前后各5个快照、旅客/设施相关ID及最小复现设计。

## 退出条件

- 所有 `VALID/INVALID` 预期满足；
- 所有 `STRESS` 无数据完整性问题；
- 252次运行全部有配对输入指纹；
- 五类故障均至少有一个真实回放证据；
- 无障碍行为若仍无旅客合同，文档继续明确为未验证。
